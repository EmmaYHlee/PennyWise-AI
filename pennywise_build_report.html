Executive summary

PennyWise AI turns raw transaction data into a conversation. Instead of filters and dashboards, users ask what they want to know — and a tool-based agent decides how to answer accurately.

PennyWise AI is an intelligent personal finance assistant designed to transform raw transaction data into actionable, personalized financial insights. The system combines LLM-powered reasoning, structured transaction analytics, and retrieval-based financial context, allowing users to interact with their finances through natural-language queries rather than traditional banking filters and dashboards. Users can ask about spending trends, transaction history, category breakdowns, and income-based analysis, while the agent dynamically identifies the appropriate intent, filters, and analytical operation to run.

The system is built on a tool-based agent architecture that separates AI reasoning from financial data access and computation — the language model decides what to compute, but never computes financial figures itself. Transaction data is enriched with standardized categories, subcategories, merchants, and metadata such as logos, enabling the agent to return both accurate financial results and rich UI experiences in the same response. The architecture is intentionally data-driven rather than hardcoded, so new transaction categories, merchants, and use cases can be supported without adding query-specific rules.

For production deployment in a mobile banking environment, PennyWise AI is designed to incorporate secure API access, authentication, least-privilege tool permissions, encryption, PII protection, audit logging, rate limiting, and transaction confirmation for sensitive actions. Production hardening would further include horizontal scalability, model fallbacks, automated evaluation, observability, distributed tracing, latency and cost monitoring, CI/CD, versioned models and prompts, and rollback mechanisms.

This architecture provides a foundation for a scalable banking assistant that can evolve from passive financial insights toward secure, personalized financial guidance — while maintaining accuracy, reliability, privacy, and operational control.

Functional coverage

Difficulty split

4 stories rated Easy — direct single-filter aggregations (category, merchant, date range). 5 stories rated Medium — require comparison across periods, pattern/anomaly logic, or combined merchant + UI enrichment (logos). 3 stories rated Hard — income-based analysis, goal tracking, and forecasting, which all require reasoning beyond the raw transaction ledger: income figures, a savings target, or a projection over time.

Coverage by capability

10 of the 12 stories map to a deterministic function already in tools.py — aggregation, filtering, grouping, period comparison, duplicate/outlier detection, and merchant-metadata lookup — so the LLM never estimates a dollar figure itself. Goal tracking and forecasting are scoped as the next two tool functions to build, following the same pattern.

What each backend file is responsible for

main.py

FastAPI application entrypoint. Owns CORS configuration, the /health liveness endpoint, and the /chat endpoint that the frontend calls for every user message.

agent.py

Holds the Gemini client, the system prompt, and the function-calling loop: sends the user message plus tool definitions to the model, executes whichever tool the model selects, feeds the result back, and returns the final natural-language answer.

tools.py

The contract layer between the LLM and the data. Declares the 13 analytics functions the agent is allowed to call — each one typed, named, and described so Gemini can pick the right one for a given question.

analytics.py

The actual computation. Pandas-based aggregation, filtering, grouping, comparison, and anomaly logic over the enriched transaction dataset. This is where every number in a response is produced — never inside the model.

Build report · Section 08

Design principles and considerations

Five principles that shaped every architectural decision in this build.

Trustworthy

Ground every financial insight in verified transaction data. The agent never answers from general knowledge about money — every claim it makes traces back to a row in the transaction dataset.

Accurate

Use deterministic backend calculations instead of relying on LLM arithmetic. Sums, averages, and comparisons are computed in pandas, not generated by the model — the LLM's job is intent recognition and explanation, never math.

Privacy-first

Apply least-privilege access and minimize exposure of sensitive financial data. Tools expose only the specific aggregation or filter needed to answer a question — never a raw data dump — bounding what any single call can return.

Scalable

Build generalized transaction and category logic rather than hardcoded merchant-specific behavior. A new merchant, category, or spending pattern is a data change, not a code change.

Actionable

Turn complex financial data into simple, understandable recommendations. Every response is designed to answer the question the user actually asked, in plain language, with the supporting transactions visible.

1 · Security & access control

highest priority
  • Deploy the agent behind the bank's existing authenticated API gateway — every request carries a verified user session, not a bare API key.
  • Give each tool a scoped, least-privilege credential: a "read spending summary" tool cannot initiate a transfer, and a transfer-capable tool requires an explicit step-up confirmation.
  • Encrypt data in transit (TLS everywhere) and at rest (encrypted data stores, encrypted logs).
  • Mask or tokenize PII (account numbers, names) before it reaches the LLM context whenever the raw value isn't required for the answer.
  • Log every tool call and its inputs/outputs to an immutable audit trail for compliance and incident response.
  • Rate-limit per user and per session to contain abuse and runaway agent loops.
  • Require explicit user confirmation before any high-risk action (transfers, payments, disputes) — the agent proposes, the user confirms.

2 · Scalability & resilience

handles load
  • Run the agent service as a stateless, horizontally scaled deployment behind a load balancer, autoscaling on request volume and latency.
  • Cache frequent, non-sensitive computations (e.g. category taxonomies, merchant metadata) to cut redundant LLM and analytics calls.
  • Move long-running or bulk analyses (e.g. a full-year anomaly sweep) to async background processing with a status/callback pattern instead of blocking the chat request.
  • Configure a fallback model or provider so a primary LLM outage degrades gracefully rather than failing the whole assistant.
  • Apply circuit breakers and timeouts around every external call (LLM provider, core banking API) so one slow dependency can't cascade.

3 · Observability

see what's happening
  • Structured logging for every request: user (hashed), intent classified, tool called, latency, and outcome.
  • Distributed tracing across gateway → agent → tool → core banking API, so a slow or failed answer can be root-caused in one trace.
  • Dashboards for latency, error rate, and cost per conversation (LLM token spend), plus tool-call success/failure rates.
  • Model-quality monitoring: sample and review agent responses for hallucination, incorrect tool selection, and unsupported financial claims.
  • Alerting thresholds on error-rate spikes, latency regressions, and unusual cost growth, routed to on-call.

4 · Release engineering

ship safely
  • Automated test suite covering tool-contract correctness, analytics accuracy, and regression prompts for common user stories.
  • CI/CD pipeline that runs the suite on every change and blocks merges on failure.
  • Version the prompt, the tool schema, and the model together as a single deployable unit — never change one without tracking the others.
  • Canary or staged rollouts for prompt/model changes, comparing quality and cost against the previous version before full rollout.
  • A documented rollback path to the last known-good prompt/model/tool version if a release regresses.

5 · Data governance & compliance

regulatory
  • Explicit data retention policy for conversation history and logs, aligned with the bank's regulatory obligations.
  • Role-based access control over who — human or service — can view raw transaction data versus aggregated outputs.
  • Clear boundary on what leaves the bank's environment: no raw PII sent to an external model provider without a data-processing agreement and masking in place.

6 · Continuous evaluation

before & after launch
  • Pre-deployment evaluation set covering accuracy, hallucination rate, tool-selection correctness, and security probes (prompt injection, data exfiltration attempts).
  • Fairness checks across user segments to ensure spending insights and language don't skew unhelpfully for any group.
  • Ongoing production sampling to catch drift — new merchants, new spending patterns, or model updates that change behavior unexpectedly.
  • A defined financial-risk failure taxonomy (see table below) reviewed on a regular cadence.
